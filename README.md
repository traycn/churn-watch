# churn-watch

**An LLM agent that reads a CRM export, flags the accounts likely to churn, and explains why. Every prompt or model change is scored automatically against a hand-labeled test set.**

A customer success manager (CSM) with 200 accounts gets a weekly CRM export and has time to call about ten of them. churn-watch ranks the book and returns, for each at-risk account, the main reason, the evidence behind it and one next step. It also proves its own accuracy: the evaluation suite below re-runs whenever the prompt, the model or the code changes, and the scores land in this README.

> All data here is synthetic and generated by [`data/generate.py`](data/generate.py). No real customer data is used.

How to read the columns:

- **Precision / Recall / F1** are for the at-risk flag. In this job, recall matters more than precision: a missed churn costs a renewal, while a false alarm costs one phone call.
- **Ambiguous cases right** is accuracy on the 14 cases where a rules model is wrong by construction.
- **Main reason right** is, among correctly flagged accounts, how often the model named the same main reason as the label.
- **Evidence verified** is the share of cited (field, value) pairs that match the CRM record exactly. Anything else is a hallucinated number.
- **Errors** counts responses that failed the schema and so never reached the CSM.

## How it works

```
CRM export (CSV)
   │  add derived fields: utilization %, 90-day change %
   ▼
Claude (one call per account, forced tool call → Assessment JSON)
   │  at_risk, risk_score, main_reason, up to 3 drivers with (field, value) evidence, next_step
   ▼
Grounding check: every cited value is compared with the source row
   ▼
Ranked CSV + one-page HTML report ("accounts to call this week")
```

```bash
make setup
export ANTHROPIC_API_KEY=...
uv run churnwatch score data/accounts.csv --model claude-haiku-5-5 --prompt v2   # writes out/report.html
make eval          # scores every model × prompt in evals/config.toml and updates this README
make eval-replay   # reproduces the published numbers from cached responses, no API key needed
make test
```

## Design decisions

**Structured output with verifiable evidence, not free-text explanations.** The model returns JSON through a forced tool call (schema in [`schema.py`](src/churnwatch/schema.py)). Each reason must cite (field, value) pairs from the record, and notes must be quoted verbatim. [`grounding.py`](src/churnwatch/grounding.py) checks every citation against the source row. A CSM will repeat these explanations to a customer, so a made-up "usage down 38%" is worse than no explanation. Unverified evidence is counted in the evals and highlighted in red in the report.

**A rules baseline as the bar to beat.** [`baseline.py`](src/churnwatch/baseline.py) is the threshold model a CS ops team could write in an afternoon: severe tickets, overdue invoices, departed champion, usage down 25%, utilization under 50%. It sees only numbers. If the LLM can't beat it, the LLM isn't worth its cost. The comparison also shows *where* the LLM adds value: reading the CSM notes.

**A test set built around the hard cases.** A test set of obvious cases would score every approach well and show nothing. 14 of 50 accounts are ambiguous on purpose, and they're scored separately.
- Some have numbers that look risky but are explained by the notes: seasonal fleets, ramping rollouts, resolved incidents, replaced champions, and late payments caused by the customer's own ERP migration.
- Others have healthy numbers with a risk only the notes reveal, such as a competitor pilot, an RFP or a vendor-consolidation data export.

**Labels reviewed by a person against a written rubric.** Labels start from the generator's scenario. I then reviewed every row against [`docs/labeling-rubric.md`](docs/labeling-rubric.md) and overrode where I disagreed, and the overrides are recorded in the labels file. The rubric was written before any model ran. Prompt v2 restates the rubric rather than being tuned on test-set failures, so the scores are less likely to reflect overfitting to these 50 rows.

**Every change is re-scored, and every run is kept.** [`evals.py`](src/churnwatch/evals.py) logs precision, recall, F1, ambiguous-case accuracy, reason accuracy, grounding, errors, cost and latency per (model, prompt). A [GitHub Actions workflow](.github/workflows/eval.yml) runs on any change to `prompts/`, `evals/config.toml`, `src/` or the test set. It commits the new scores and this table. The history is in [`evals/results.csv`](evals/results.csv), and every miss is listed in [`evals/misses.md`](evals/misses.md) for error analysis.

**Cached, replayable responses.** Responses are cached by a hash of model, prompt, schema, record and settings. Re-running an unchanged config costs nothing. `--replay` reproduces the published numbers with no API key, and the test workflow checks that it does.

**Small model by default.** Scoring is one short call per account, so the default is Claude Haiku 5.5, with Sonnet 5.5 as the comparison. The table shows what the larger model buys per 1,000 accounts.

## Limitations

- **Synthetic data.** The accounts and notes come from templates, so real CRM notes will be messier, shorter and often missing. The numbers here show the approach works on cases constructed to need judgment. They are not a forecast of production accuracy.
- **No outcome labels.** Labels encode what a reasonable CSM would conclude today, not whether the account actually churned later. A production version would score against real renewal outcomes.
- **50 accounts is small.** One account is 2 points of accuracy, so differences of a few points between configurations are noise.
- **One account at a time.** The model doesn't compare accounts or see history beyond the 90-day fields.

## Next steps
